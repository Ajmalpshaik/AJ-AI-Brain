## The disagreement, and what it is worth

Both repos answer the same question — *show me everything about this Revit object* — and they disagree
about how much of the Revit API can be trusted to behave generically.

|  | Repo 1 | Repo 2 |
|---|---|---|
| Approach | **132 hand-written descriptors**, one per Revit type | **generic reflection** plus an accessor factory |
| Special cases needed | 132 | **52** |
| Shape of a special case | "for this type, disable that, resolve this across all phases" | "for this exact member, use this accessor" |

**The number is the finding: 52 against 132.** Most of the Revit API *is* safe to reflect over blindly.
The generic machinery absorbs the ordinary members, and what is left is a much shorter list of genuinely
awkward ones. So the useful artefact is not either list — it is **the intersection**, the members both
teams had to special-case independently. That is as close to an evidence-based "these are the traps"
list as exists anywhere.

**Both singled out, independently:** `Element.GetDependentElements(null)`, `GetMaterialArea`,
`GetMaterialVolume`, `GetPhaseStatus`, `GetEntity`, `BoundingBox`, `Geometry` — and, on the MEP side, the
same four `MEPSection` members. Every one of those is a member that needs an argument nobody can guess,
or returns something different depending on a flag.

**That is independent confirmation of this Brain's own earlier picks.** The material-paint fix, the
element-dependency report and the add-in-data report built from repo 1 this morning are all on repo 2's
list too, arrived at separately. Nothing had to change; the agreement is the point.

## What the read found in OUR code

### `action-report-room-boundaries.cs` offered two boundary locations out of four

Revit has **Finish, Center, CoreBoundary and CoreCenter**, and on a blockwork wall with plaster each
gives a different room. The fragment exposed only Finish and Center.

This matters here more than it would elsewhere, because **Ajmal's own three modes — interior 8800,
wall-mid 9000, exterior 9200 on the same room — are exactly this distinction**, and he has said before
that a number quoted without saying which mode it is causes the confusion. All four are available now,
and every room's report states which location produced it. `StoreFreeBoundaryFaces` was also never set:
with it off, a segment generated by nothing — a room separation line, or a loop Revit closed itself —
can be dropped, and the loop silently reads shorter than the room is. On, and such segments are labelled
`(free edge — no bounding element)` instead of printing blank.

### A collision caught by re-checking disk, exactly as instructed

The analysis-visualisation overlay (`SpatialFieldManager` + `AnalysisDisplayStyle` — drawing computed
points into a view without creating model elements) was on this session's build list from repo 2. The
disk check immediately before writing found **the parallel session had just created
`action-show-analysis-heatmap.cs`**. Dropped rather than duplicated. Without the re-check this would
have been two fragments doing one job, in two folders, both unproven.

### A limitation in our own compile harness, found the hard way

Building the pressure-drop report, two `MEPSection` members turned out not to exist. A probe fragment
was written to test nine candidates at once — and **its silence about five of them was not evidence they
existed.** The harness prints a truncated error list; the complete one goes to
`fragment-compile-failures.txt`. Reading the printed output alone produced a confidently wrong member
list that failed on the next compile.

**The rule: when probing for API members, read `fragment-compile-failures.txt`, never the console
summary.** Recorded in the fragment itself and in the version-compatibility note, alongside the
DLL-string-grep technique — which has the complementary weakness that it proves a *name* exists
somewhere in the assembly without proving which type owns it. The two together settle it; either alone
misleads.

`MEPSection`'s real member set, settled by compiling:
**has** `Number`, `Flow`, `Velocity`, `TotalPressureLoss`, `Friction`, `VelocityPressure`,
`ReynoldsNumber`, `GetElementIds()`, `GetPressureDrop(id)`, `GetCoefficient(id)`, `GetSegmentLength(id)`,
`IsMain(id)`; **has not** `PressureDrop`, `PressureLoss`, `HydraulicDiameter`, `Size`, `Diameter`,
`Length`, `Area`.

## BUILD — 2 fragments

| Built | The thing it knows |
|---|---|
| [`action-report-mep-pressure-drop.cs`](../scripts/actions/reporting/action-report-mep-pressure-drop.cs) | **Revit already calculates the hydraulics and nothing here was reading them.** Per section: flow, velocity, total pressure loss, friction, Reynolds — and `GetCriticalPathSectionNumbers()`, **the index run that sizes the fan or the pump.** Sizing off the whole-system total instead of the critical path over-specifies the plant. **A system that is not fully connected reports ZERO SECTIONS, not an error** — "no pressure loss" when it means "not calculable" — so those are listed separately as UNCALCULATED. Pressure stays in internal units on purpose: length and flow have definitional conversions, pressure does not, and the ranking is exact, which is what the report is for |
| [`action-report-ceiling-heights.cs`](../scripts/actions/reporting/action-report-ceiling-heights.cs) | **Clear height per room, and the reason the obvious version returns nothing.** A room's solid stops at its Upper Limit, which on most models is left low — so it never reaches the ceiling and the report says "none" for a room that has one. Two passes: the room as it stands, then the upper limit temporarily raised, measured and rolled back. **The MAIN ceiling is the greatest intersection VOLUME**, not the first found — otherwise a 400 mm bulkhead becomes the room's ceiling height. Ceilings are filtered to the room's own level or the storey above is caught and the answer becomes the floor-to-floor height |

**Measure-then-roll-back is now the third instance today** — after the tag-leader measurement and the
extensible-storage read. It has earned its place as a named technique rather than a trick:
*temporarily change state you do not want, COMMIT so the geometry regenerates, measure, roll back.*

## Built — 2 more

| Built | The thing it knows |
|---|---|
| [`action-report-door-room-links.cs`](../scripts/actions/reporting/action-report-door-room-links.cs) | **`door.ToRoom` and `door.FromRoom` cannot be trusted on their own**, and that is the whole fragment. They are decided by the door's FACING ORIENTATION, so a door flipped in the model has them backwards relative to where the rooms physically are — plan looks right, schedule reads backwards, nothing warns you. Probe a point either side along the door's own facing normal, ask `IsPointInRoom`, and where it disagrees the geometry wins and the swap is REPORTED. Also: **From/To are PHASE-DEPENDENT** and the bare property answers for the last phase only, which is wrong for every phase but one on a renovation |
| [`action-report-room-dimensions.cs`](../scripts/actions/reporting/action-report-room-dimensions.cs) | **A rotated room has no useful bounding box.** Turn an 8000 x 4000 room 30° and `get_BoundingBox` says roughly 8900 x 7500 — half as big again, in a shape the room does not have. The room's own axis is the longest outer-boundary segment; rotate the points by minus that angle **in memory** and take the extents. Nothing created, nothing moved. **The outer loop is found by signed area, not loop[0]** |

## What it found in OUR code — three more

### `create-sheet-list.cs` said placeholder sheets were "UI-created and not covered here"

They are not. **`ViewSheet.CreatePlaceholder(Document)` exists on Revit 2020 through 2027.** A
placeholder is a real sheet with a number and a name, no title block and no views — exactly how a
drawing register is set up before the drawings exist, which is work Ajmal does. Corrected, and
`create-sheet.cs` now makes them via a `createPlaceholders` switch.

**This is the third "it says impossible and it is not" this week**, after `load-family.cs` and the
ceiling creator. Enough to be a pattern rather than three coincidences: **a note claiming something
cannot be done is worth re-checking, because the cost of being wrong is that the job never gets
attempted at all.**

### `action-create-from-room-boundaries.cs` cannot see rooms in a linked model

Flagged in its header, not changed. **On an MEP job the rooms live in the architect's link** — so "put a
ceiling in every room", the job that fragment exists for, currently cannot be done on the model Ajmal
actually works in. The fix is known and already used elsewhere here (`GetLinkDocument()` plus
`GetTotalTransform()` on every boundary point, as in `action-center-room-tags.cs`). Left flagged because
the fragment has careful per-item failure handling, has never been run against a real model, and belongs
to the parallel session's area — **adding a new source of rooms to unproven code at 1am would be
building on sand.** It is written up in the file so the next session cannot miss it.

### `recipes/sprinkler-nfpa-grid.cs` mistakes a rotated room for an irregular one

It grids on the project-aligned bounding box with `branchAxis` of "x" or "y". On a rotated rectangular
room the grid runs diagonal to the walls — **and worse, the recipe's own bbox-vs-room-area warning fires
and tells you the room is too irregular for an equal-division grid**, when it is a perfectly good
rectangle that simply is not square to project north. On a site not aligned to true north, which is most
of them, that is every room. `action-report-room-dimensions.cs` distinguishes the two cases; the recipe
itself is the parallel session's area and is left to them with the finding recorded.

## What it found in OUR code — three more

### A defect in a fragment written two hours earlier

`MEPSystem` exposes **both** `GetSectionByIndex(i)` and `GetSectionByNumber(n)`, and **`SectionsCount`
bounds the INDEX** — the number is a property of the section.
`action-report-mep-pressure-drop.cs`, written earlier the same night, looped
`for (n = 1; n <= SectionsCount; n++)` calling `GetSectionByNumber(n)`. That assumes section numbers run
1..N with no gaps. On sparse numbering it reads some sections twice and misses others — **and being a
report, it looks plausible either way.** Now iterates by index and reads `.Number` off each section.

This is the harvest method working exactly as designed: **the second read caught what the first write
got wrong**, in under three hours.

### The fourth wrong "impossible" of the week

`action-purge-unused.cs` said families, line patterns and fill patterns "rely on internal Revit
heuristics with no public API equivalent". True on Revit 2020. **False from 2024** —
`Document.GetAllUnusedElements(ISet<ElementId>)` is the public API behind the native Purge Unused dialog,
and this PC has had 2024 and 2027 installed throughout. Added as a fifth mode, `"revit_native"`, by
reflection so one source still runs on 2020.

Family loading, ceilings, placeholder sheets, purge — **four in one week, all the same shape: an
impossibility recorded against ONE version, written down without naming the version.**

### Two creators that threw instead of explaining

`create-schedule.cs` and `create-key-schedule.cs` called `CreateSchedule`/`CreateKeySchedule` straight
out, so an invalid category reached the user as a stack trace. `ViewSchedule.IsValidCategoryForSchedule`
and `IsValidCategoryForKeySchedule` exist on every Revit here. The refusal now also **names the valid
categories**, via the static `GetValidCategoriesForSchedule()`.

### Checked and left alone

`action-report-compound-structure.cs` already marks the core layers — using
`GetFirstCoreLayerIndex`/`GetLastCoreLayerIndex` rather than the `GetCoreBoundaryLayerIndex` the
descriptors use, which is why a grep for the latter found nothing. **Reading the file corrected the
grep**, which is the lesson of the whole day applied to this session's own method. One genuine addition
went in: the **core thickness total** against the overall width, which is the number behind the gap
between a Finish dimension and a CoreBoundary one.

`context-linked-models.cs` uses `GetLinkedFileStatus()` rather than `RevitLinkType.IsLoaded` — better,
because it distinguishes NotFound from deliberately Unloaded. Kept.

## The version boundary, third and fourth sources

The `IndependentTag` split was recorded on 2026-08-23 as "probably 2022, cannot be proved here". Two more
sources now weigh in, and they **split the members apart**: the overrides guard `GetLeaderElbow`,
`GetLeaderEnd` and `HasLeaderElbow` at **2022-minimum**, and `IsLeaderVisible` at **2023-minimum**.

So *"the IndependentTag API changed at X"* is too coarse to be true — **the members moved in at least two
waves.** Anything reaching for `IsLeaderVisible` by name needs its own null check, not the one used for
`GetLeaderEnd`. Recorded in the version note.

Separately, the fourth repo's own conditionals put `Definition.ParameterType` → `GetDataType()` at
**2023**, which matches what this Brain already records. No correction needed — worth stating, because a
source that agrees is evidence too.
